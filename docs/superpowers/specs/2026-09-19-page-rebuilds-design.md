# Page Rebuilds — Design Spec

BlueStaffyUK rebuild, project 4 of 6. Date 2026-09-19. Branch `page-rebuilds`, cut from
`foundation` at `63a7b12` (the project 3 merge). No remote; nothing is pushed.

Approved in the brainstorm on 2026-09-19. Decisions taken there are locked facts of this spec:
full rewrite per page through the board system (not a re-skin); three rendered styles per
section on every board; all eleven rich pages rebuilt and every URL kept; the three real reviews
rotated with `REVIEW_PLACEHOLDER` slots for the rest.

## 1. Goal and scope

Project 4 rebuilds every rich page on the project 3 kit, each written fresh from an approved
outline through its own page board, and fixes the facts the migration carried wrong. It adds the
two navigation components the original site had and the kit lacks: the desktop dial and the
mobile section jump links.

**In scope.** The eleven rich pages (`/`, `/blue-staffy-uk-breeders/`,
`/buy-blue-staffy-puppies-uk/`, `/blue-staffy-pup-sale-uk/`, `/buy-staffy-puppies-for-sale-uk/`,
`/blue-staffy-health-uk/`, `/uk-staffordshire-bull-terrier-guide/`,
`/uk-blue-staffy-puppy-buying-guide/`, `/uk-blue-staffy-breeders-contact/`,
`/privacy-policy-uk/`, `/thank-you-blue-staffy-puppies-journey/`), the blog index
`/blue-staffy-blog-guides/` and its one post; the kit shell (header, footer, dial, jump links)
on the three hubs and the puppy pages without rewriting their content; the Glasgow → Carlisle
change in content, `data/settings.json` and schema (closes Known Issue 16); the locked prices,
the byline, the three duplicate headers (Known Issues 9, 11, 12); `generate_page_dates.py`
wired so `dateModified` is real (Known Issue 8, 20); the form-contract option value.

**Out of scope.** The 28 location pages, the comparison cluster and the two new blog posts
(project 5); domain, phone, GSC, GA4, Bing, IndexNow (project 6); any new photography (rule 11:
existing images and videos are reused, never replaced).

## 2. Locked decisions

| Decision | Pick | Alternatives considered |
|---|---|---|
| Depth | **Full rewrite per page through the board** | re-skin + fact fixes; rewrite money pages only |
| Board shape | **Three rendered styles per section, pick per section** | three whole-page styles |
| Page set | **All eleven rich pages + blog, every URL kept** | six named pages; consolidate the three sale pages with 301s |
| Reviews | **Rotate the three real reviews; empty slots are `REVIEW_PLACEHOLDER`** | reviews only where they were; wait for more |
| Navigation | **Desktop dial (sticky sidebar, progress ring, numbered list, scroll-spy) + mobile section sheet and bottom tab bar** | none |

Distinct intent per overlapping sale URL: `/buy-blue-staffy-puppies-uk/` = the listing and how
to buy; `/blue-staffy-pup-sale-uk/` = price, deposit, delivery and what is included;
`/buy-staffy-puppies-for-sale-uk/` = why this breeder (health testing, home raising, KC,
after-care). The outline step records each page's intent and the dup gate holds them apart.

## 3. Components 14 and 15

**`PageDial.astro`** (desktop, ≥1024px). A sticky sidebar card in a `196px minmax(0,1fr)` grid
with `gap: 28px`: a 64px progress ring (50px inner) showing `n of N` in Fraunces, then a
numbered section list (rows ≥24px, dashed top rule) with the active row set by an
IntersectionObserver scroll-spy. `position: sticky; top: calc(var(--hdr-measured, var(--hdr))
+ 16px); max-height: calc(100vh - var(--hdr) - 32px); overflow-y: auto`. Tokens only; card
shell from `kit.css`; numerals ≥4.5:1. Props: `sections: {id,label}[]`, `title?`.

**`SectionSheet.astro`** (mobile and tablet, <1024px). A fixed bottom tab bar (`Home`,
`Puppies`, `Contact`, `Sections`; 44px targets; inline stroke icons; hidden on print) whose
`Sections` tab opens a bottom sheet (`<dialog>`, native, `inert` background) listing the same
sections with the same scroll-spy state and a CTA button. Props: `sections`, `ctaLabel`,
`ctaHref`. The page's `scroll-margin-top` accounts for the header only; the tab bar sits below
content so no jump target lands under it, and the harness's `nav-jump-target-lands` check gains
a bottom-chrome measurement (the source repo's `bottom-bar-under-tabbar` idea, Known Issue 10)
so the tab bar can never cover a target.

Both components take three styles on the first page board (contact) and are then fixed for
every page. `tests/py/test_design_components.py` gains dist assertions for both on
`/kit-preview/`; `components.json` grows to fifteen rows; the Design System artifact gains two
previews (regenerated by `scripts/build_design_system.py`).

## 4. The page board

One board per page, built by `scripts/build_page_board.py` (extended, re-palette'd to the
tokens) from the board record `data/boards/<slug>.json`, published as an Artifact with the
database capability, picks pulled by `scripts/board_approve.py`. A board holds:

1. **Outline.** H1; the ordered section list with H2–H6 per section, each section's purpose,
   word target and the facts it must carry (from the migrated page's body, `data/settings.json`,
   `data/puppies.json`, `data/faq.json`, `data/reviews.json`); key takeaways; review slots
   (top / middle / bottom, each `single` or `grid`); FAQ rows; internal links (target + intent);
   the images the page reuses (from `data/image-manifest.json`, by original path) and the
   YouTube embed(s); the meta title (three options) and description (three options); the
   competitor scan summary (3–5 UK Staffy breeder pages for the same intent: sections, word
   counts, FAQs, schema — recorded as data, `NOT FETCHED` where unavailable).
2. **Three styles per section.** S1/S2/S3, each rendered at 1280 / 768 / 375 from the kit with
   the section's real outline copy on a hidden noindex route `/board-preview/<slug>/` (one
   `[data-section][data-style]` block per combination; the `NON_CONTENT_ROUTES` exclusion and
   its self-expiry test cover it). `scripts/build_board_previews.py` reuses
   `scripts/_kit_sections.py` to cut the built route into per-style HTML snippets embedded in
   the board (inline, no artifact assets needed), styled by the same inlined CSS as the canvas.
   Styles differ in structure, not tokens (the project 3 distinctness rule applies).
3. **Picks.** Per section: style S1/S2/S3; per review slot: mode; the dial style (contact board
   only); the meta title and description; a note per section. Saved to `boards/<slug>` in the
   board's database in the shape `board_approve.py` already reads (`picks`, `notes`,
   `approved_at`, `record_hash`).
4. **Approval.** `board_approve.py <slug>` verifies the record hash, writes the picks and
   `status: approved` into the record, and `board_gate.py <slug>` refuses a build whose board
   is not approved or whose picks are incomplete.

## 5. Writing and content rules

- **Fresh prose from the outline** (working rule 8), first person as Lisa Bright (rule 1),
  facts only from: the migrated page body, `data/*.json`, `rules/`, the competitor scan
  (structure and topics only, never their claims). No claim without a source; unknowns are
  `NOT FETCHED`; statutory and licence claims stay `LICENCE_CLAIM_PLACEHOLDER` /
  `LEGAL_CLAIM_PLACEHOLDER` until Lisa confirms them.
- **Facts preserved.** `scripts/facts_preserved_check.py` (new) extracts from the migrated
  page: every price, puppy name, health test, credential phrase, image path and embed id, and
  asserts each appears on the rebuilt page or in the board record's `dropped` list with a
  reason. Replaces `migration_parity.py` for rebuilt pages (the parity gate keeps running for
  pages not yet rebuilt; a rebuilt page is removed from its target list).
- **Titles and descriptions.** Honest, descriptive, keyword-leading; the "No.1 BEST", "THE BEST
  3", counts-in-title and year-stamped patterns are removed. Title 50–60 chars, description
  140–160, three options each on the board.
- **Location.** `Carlisle · Cumbria` everywhere; `data/settings.json` `address` becomes
  `{"city": "Carlisle", "region": "Cumbria", "country": "GB"}` with no street, postcode or
  coordinates until Lisa gives them (Known Issue 16); the Glasgow location page keeps its URL as
  an outreach page (project 5 rewrites it); `scripts/form_contract_audit.py`'s `PUPPY_OPTION` and
  `ContactForm.astro` are re-based to the kit form's option set.
- **Reviews.** `data/reviews.json` rows only; each page's board chooses which of the three
  real reviews fill which slot and in which mode; every unfilled slot renders
  `REVIEW_PLACEHOLDER` visibly and the gate report counts them, so the number of reviews the
  site still needs is a measured figure. Review quotes are whitelisted for the dup gate as
  sitewide lines.
- **Images and video.** Every image the old page carried is reused with its original path and
  alt text (working rule 11); new placement only. YouTube embeds keep their ids. No new
  photography. Puppy photos through `astro:assets` as in project 3.
- **Headings.** H1 unique; H2–H6 present where the outline needs them (the `all_six_levels`
  audit stays advisory); Title Case per `rules/headings.md`; no header collides with another
  page's (`board_gate.py` header-collision at 0 for rebuilt pages).
- **Links.** Link-first anchors (`rules/links.md`), anchor text varied, every internal target
  resolves (`redirect_check.py` at 0), external links only to sources the copy cites.
- **FAQ.** Page FAQs live in `data/faq.json` with `source` = the page; `FAQPage` schema from
  the same rows; answers backed by page copy.
- **Dates.** `scripts/generate_page_dates.py` wired into the build (`data/page-dates.json`
  regenerated from git), `dateModified` on every page from it; `schema-date-modified-present`
  rows go to 0 on rebuilt pages.
- **Query augmentation.** For each page, the outline step expands the primary keyword into
  the questions and entities AI search asks and maps each to a section or FAQ; recorded in the
  board record. No dedicated skill yet (Known Issue 17); the step is written into the page
  builder skills.

## 8. Risks

- *Twelve pauses for picks.* Boards are published as each outline is ready, so several can be
  picked in one sitting; the build order never blocks on a later page's picks.
- *Only three real reviews.* Placeholders are visible and counted; nothing is invented.
- *Competitor scan needs the network.* Firecrawl / web search is available in-session; where a
  fetch fails the scan records `NOT FETCHED` and the outline proceeds from the migrated page.
- *Bottom tab bar covering jump targets.* Measured by the new harness check before the first
  page ships.

## 9. Amendments

Recorded here as they happen.

**Amendment 1 (2026-09-19, Tasks 1–2).** Two corrections to §3.

1. **`nav-bottom-chrome-clear` is a SEPARATE check, not an extension of
   `nav-jump-target-lands`.** They are siblings at opposite ends of the viewport and they
   cannot be one check. `nav-jump-target-lands` measures a target against the chrome pinned
   to the TOP, which `scroll-margin-top` answers, and it has to defeat smooth-scroll timing
   to do it — `forceInstantRootScroll`, a settle probe, a budget and three defect buckets.
   The bottom has no CSS answer at all: a `position: fixed` bar is out of flow, so the only
   fix is for the bar to reserve its own height in the body, and the measurement is pure
   geometry against an element that never moves. Folding the two together would put a
   timing-sensitive scroll harness in front of a question that does not need one, and would
   merge two failure modes with two different remedies into one defect row. They are
   registered separately in `tests/render/checks/nav.ts`, both blocking, both NAV.

2. **The 196px dial column lives in `PageShell.astro` (Task 3), not in `PageDial`.**
   `PageDial` owns the card and sets its own `width: 196px`, but the page GRID that gives
   the column its place beside the prose — and collapses it below 1024px — belongs to the
   shell every rebuilt page mounts. A component that declared the grid would be deciding
   the page's layout from inside a sidebar, and the two hubs would each need their own copy.

**Amendment 2 (2026-09-19, Task 7 and the board pipeline).** Two gate rulings, both taken
after the first three approvals (privacy, thank-you, contact) were applied and the gate was
run against them.

1. **`min-h5-h6` reads the BUILT page for a rebuilt slug, and the record tree otherwise.**
   The check counted H-levels off `all_headings(board)` — the board record's own tree — so
   the only way a rebuilt page could meet the floor of five H5 and five H6 was for an
   approved outline to be reopened and padded with ten sub-headings the breeder never saw,
   purely to satisfy an arithmetic check. That inverts the board: the outline is a plan for
   sections, agreed at H2 and H3, not a transcript of every sub-point. From now on, when a
   slug is listed in `data/facts/rebuilt.json` and `dist/<slug>/index.html` exists, the
   floor is counted off the built page, which is how the migrated pages met it too — H4 and
   H5 sub-points and the `tuple.h6_prefixes` "Note:" lines are written inside the sections
   at build time. A record that is not yet rebuilt, or one whose page has not been built,
   keeps the tree reading: a missing build is not a pass, and reading zero headings out of
   nothing would clear the floor for free. The finding names its source either way.

2. **`ledger-triple-owned` becomes `ledger-tuple-owned`, on hero+faq+takeaway.** The old
   signature was hero+dial+rail, on the reading that those three are the page's chrome and
   two pages wearing all three the same way are the same page. Task 9 retired that premise:
   the breeder picks ONE dial style and ONE sheet style on the contact board and both are
   baked into the kit, so every rebuilt page carries the same two and the signature
   degenerates to "no two pages may share a hero style". It failed privacy-policy-uk
   against thank-you-blue-staffy-puppies-journey on a shared hero S3 alone, although the
   two pages differ in their FAQ shell and their takeaway set. The signature is now the
   tuple minus the two baked axes — what a page is made of that the breeder can still
   choose differently — and the two records separate on `faq-s1` against `faq-s3`.

3. **2026-09-19, user request during the first boards.** (a) Working rule 12: every page board lists every internal and external link the page will carry, per section and as one page table, before approval; the three boards already approved are rebuilt with the old pages' body links carried in and re-approved. (b) **Component 16, `SectionStrip`**: a sticky horizontally-scrolling rail of numbered section chips (`01 Label · 02 Label …`) under the header on mobile and tablet (<1024px), scroll-spy active chip, thumb-scrollable, matching the source site's home section strip; it complements the bottom sheet (the strip for quick jumps, the sheet for the full list). Three styles on the contact board; then fixed site-wide like the dial and sheet. `nav-bottom-chrome-clear`'s top-chrome counterpart: the strip's height is added to `scroll-margin-top` via `--hdr-measured` so no jump target lands under it.

4. **2026-09-20, after the first rebuilt page.** (a) Word bands: a record's section band counts the section's own prose; the H4–H6 ladder the built page adds to meet `min-h5-h6` (≈25–30 words per section) and FAQ accordion answers (from `data/faq.json`) sit outside the band. `board_gate` measures the band on the built page's prose excluding those two, and the page-level target is the sum of section bands plus the ladder allowance. (b) Headings: the breeder approves heading WORDING; case is presentation. Rebuilt pages render H1–H6 in Title Case per `rules/headings.md`, so `sem-title-case-headings` stays a rule, not a per-page choice. (c) `final_page_audit.py` rules that assume a sales or guide page (`lifespan_12_14`, `newsletter_present`, `cites_credentials_early`) apply by page type: `interior` legal/utility pages (`privacy-policy-uk`, `thank-you-…`) are exempt and the audit says so per page; `phone_in_footer` stays a project-6 baseline row on every page.

5. **2026-09-20, user request.** Working rule 13: every table on a rebuilt page is a `table`-shaped board section with three rendered styles (kit `DataTable` component 17: S1 ruled rows with a brand header band, S2 zebra card, S3 borderless with brass column rules — all three stack into `data-label` rows below 640px, tested by the harness's stacked-table check), and `tuple.table` records the pick. Pages that carry tables: pup-sale (price and delivery bands), the two guides (breed facts, health tests), buy-staffy (reasons/comparison), homepage (at a glance).


6. **2026-09-20, build review of the first three rebuilt pages.** Seven rulings, taken after
   `/privacy-policy-uk/`, `/thank-you-blue-staffy-puppies-journey/` and
   `/uk-blue-staffy-breeders-contact/` were read side by side. Referred to elsewhere as
   amendment 6a-6g, in this order.

   (a) **A kit component may not assert a page's credentials or invent its links.**
   `Hero.astro` hard-coded three trust chips ("KC registered", "DNA-tested parents", "Raised
   in the home") and two CTA buttons. On the homepage those are true and approved; on a
   privacy policy they are a sales line, and the two buttons were two hrefs no board record
   listed. Both are props now, both default to NONE, and the specimen on `/kit-preview/`
   passes the homepage's set through the registry. The three rebuilt pages pass neither:
   their records give the hero no `cta` and no links.

   (b) **Link parity is a gate.** `scripts/link_parity_check.py --check` walks `<main>` on every
   slug in `data/facts/rebuilt.json` minus the in-page nav chrome, and diffs the hrefs both
   ways against the record's `sections[].links`: an extra fails, a missing fails, and an
   href in `dropped.links` fails as its own kind. It runs in `check:all` directly after
   `check:facts`, which is the other half of the same question — facts-preserved asks what a
   rebuild LOST, link parity asks what it ADDED. Two exemptions, both narrow and both
   written into the script: same-page `#fragments` (owned by `nav-anchors-resolve`), and the
   puppy grid's own card links, which are rows of `data/puppies.json` rendered by
   `PuppyCard` on a section of shape `puppies` and would go stale in a record the day a
   litter changed. `mailto:` is NOT exempt; the three pages state the address as text.

   (c) **`dropped.text`: a claim can leave a page without a token going missing.** The fact set's
   six kinds are tokens — a price, a name, a test, an image. A migrated body also makes
   CLAIMS, and a rebuild that simply does not rewrite one drops it silently.
   `facts_preserved_check.py` now extracts the migrated body's claim sentences (those
   carrying a number, a named organisation or a named process) and asserts each is either
   restated on the rebuilt page or listed under `dropped.text` with a reason. Presence is
   two tests: every HARD trigger (numbers, organisations) must appear, and at least six of
   the claim's content words. A process word qualifies a sentence as a claim and then counts
   as an ordinary word — "review and respond" is honestly rewritten "read and answered", and
   demanding the verb back would be demanding the old sentence back. All twelve fact sets
   carry the kind; the nine unrebuilt ones captured theirs while their bodies still exist.

   (d) **`dropped` leaves `record_hash`.** It is the accounting of what the rebuild did not
   carry and cannot be complete before the rebuild exists, which is after approval by
   construction — the same argument that already excludes `assets[].status` and `.file`,
   which the bake fills in. Hashing it made ruling 3 unusable on every approved record: the
   only ways to log a dropped claim would have been to re-board a page the breeder had
   signed off or to re-stamp a hash by hand. The three approved records were re-stamped
   once, each with the proof recorded in the commit that the OLD formula minus the new
   `dropped.text` key reproduces the stored hash exactly, so nothing outside `dropped` moved.
   `approval_matches` also accepts the old formula, for records whose `dropped` is untouched.

   (e) **A privacy policy renders its real last-updated date.** Four sentences of that page lean
   on a date the page did not show. `src/components/kit/PageDate.astro` renders it from the
   same `data/page-dates.json` row `BaseLayout` puts in the WebPage node, so the visible date
   and the machine-readable one cannot disagree, and a route with no row renders nothing
   rather than today. The `no_visible_date` rule stays what it was: freshness belongs in the
   schema on a sales page, and this is the exception that rule was never about.

   (f) **Every H4–H6 ladder sentence traces to the migrated body or to `data/`.** The ladder is
   written at P5 rather than approved on the board, which is exactly why it is where an
   invented claim lands. Nine were reworded across the three pages — "there is no list",
   "no fee, and no effect", "no archive of old wordings", "most often ends up", "usually
   saves two more" and the like. The test is the same as for body prose (rule 9): a sentence
   states what a file on disk says, or it states nothing.

   (g) **FAQ question headings take Title Case.** `rules/headings.md` exempted them on the
   ground that they "live in `<summary>`, not a heading tag". `Faq.astro` puts an `<h3>`
   inside the summary — which is what makes the answers navigable as a heading list — and
   both title-case checkers select every `h1`–`h6` under `<main>`, so the exemption was one
   no checker implemented. The question is cased at RENDER through the same `titleCase()`
   the pages use; `data/faq.json` keeps the sentence-case wording, which is what the FAQPage
   schema's `name` and the dup gate read.
