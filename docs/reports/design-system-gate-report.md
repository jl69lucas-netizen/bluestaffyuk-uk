# Design system gate report

BlueStaffyUK rebuild, project 3 of 6. Written by hand from the real outputs of the two full
runs recorded in `docs/reports/design-system-run.log`, the Lighthouse sweep, and the gate
scripts re-run at close-out. Date 2026-09-19. Branch `design-system`, no remote, nothing
pushed.

Spec: `docs/superpowers/specs/2026-09-18-design-system-design.md`. §9 is the definition of
done **as amended by §11 (amendments 1–7)**; the checklist at the end answers it line by
line in its amended form. Where §9's literal text and an amendment disagree, the amendment
wins: the Claude Design prompt pack is replaced by the published Design System artifact, the
mark is the L1 badge rather than a stroke drawing, the `/design-canvas/` route became
`/kit-preview/`, the canvas is 39 boards rather than 65, and `Testimonial` carries modes.

Read the two severities differently, as in project 2. The **system gates** — parity,
redirects, schema, sitemaps, the marker gate, both registries, the render baseline checker
and pytest — are zero-tolerance and are all at zero. The **content audits** (final page,
page hardening, duplicate content, AEO, evidence) and the **render pages** run report large
non-zero counts against body HTML that is still Foundation's verbatim WordPress migration.
This project built a component kit and mounted none of it on a real page except the shell,
so those counts are a carried baseline, not defects introduced here. Every such number is
tagged **baseline** or **regression**; there are no regressions.

**One earlier controller statement is corrected here.** During Task 16 the controller
reported `npm run test:render:pages` as "0 failed". That was a stale-scorecard artefact — the

## Tokens

`src/styles/tokens.css` holds **66** custom properties in a three-layer `@theme` — primitive,
semantic, component — and rule 1 in `rules/design.md` forbids a hex anywhere else under
`src/`. The hex ban is enforced by a strict-xfail pair so that a test which stops finding
violations fails rather than passing vacuously.

| | |
| --- | --- |
| `tests/py/test_design_tokens.py` | **10** tests |
| `tests/py/test_brand_assets.py` | **7** tests |
| `tests/py/test_design_picks.py` | **5** tests |
| `tests/py/test_design_components.py` | **37** tests |
| `data/design/contrast.json` | **20** foreground/background pairs, every one asserted at WCAG AA by `test_contrast_pairs_clear_aa` |

**The brand-tint alias.** `--color-brand-tint` is declared as `var(--color-steel-300)` rather
than as its own hex. It exists because the mark's skull needs a light steel that is already in
the palette: giving it a new literal would have put a fourteenth blue in the system and broken
rule 1's "one hex per primitive". It is the one semantic colour token in the file that names
another token in the same family instead of a value, and the Design System artifact carries
the same relationship as `"{color-steel-300}"` (spec §11 amendment 7a).

Brass (`--color-cta`) is documented in `_registry.ts` as a fill with `--color-cta-ink` text, or
an accent on a dark band, and never the colour of small text on a light surface, where it
measures 2.1:1.

## Logo

**The mark is the L1 badge** (spec §11 amendment 3a): a flat-shaded cartoon Staffordshire Bull
Terrier head — broad skull, rose ears, white blaze, breed grin with a brass tongue — inside a
steel roundel with a brass ring. The original stroke-based, `currentColor` mark was voided at
the user's review because the line drawing did not read as the breed. The geometry lives once
in `src/components/kit/markShapes.ts`; `MarkSprite.astro` emits `<symbol id="bsuk-mark">` and
`<symbol id="bsuk-mark-inverse">` once per document from `BaseLayout`, and `Mark.astro` is a
`<use>` at one of them, with a `standalone` prop that inlines the paths for the self-contained
lockup documents (amendment 4e). `dist/index.html` carries **2** `<symbol>` elements and **2**
`bsuk-mark` references, which is the sprite working as designed.

**Four lockups**, generated by `scripts/build_lockups.py` from the mark and the tokens:

| File | Bytes | Use |
|---|---:|---|
| `public/brand/logo-horizontal.svg` | 15,087 | site header, inlined with `?raw` |
| `public/brand/logo-stacked.svg` | 15,110 | tall placements |
| `public/brand/logo-mono.svg` | 15,394 | inverse bands — the footer |
| `public/brand/logo-icon.svg` | 1,463 | the badge alone; the favicon source |

**Four favicon renders**, generated by `scripts/build_favicons.py` from `logo-icon.svg`:
`public/favicon.svg`, `favicon-32.png` (32), `apple-touch-icon.png` (180) and `icon-512.png`
(512). `icon-512.png` is not only a favicon — it is also the raster the JSON-LD `image` points
at, which is why it is built rather than hand-exported.

**The mono treatment decision, and why the footer uses it.** Task 20's text said the stacked
lockup in the footer at 96px. That is wrong and was not followed. The footer is an inverse
band (`data-surface="inverse"`), and the stacked lockup is self-coloured: its wordmark is
`--color-brand`, which is steel-700 — the band's own background — so it would render
invisible. The mono lockup is the one built for this case: `currentColor` over three tones, so
it takes the band's bone text colour. The deviation is recorded in a comment at
`src/components/SiteFooter.astro:9`. The header inlines `logo-horizontal.svg`; the footer
inlines `logo-mono.svg`; both use `?raw` at build time so neither costs a request.

Mark variant **L1** was picked separately from the component picks, in a second round.

**Two props survive the prune, both renamed to what they are** (amendment 4b). `Button.kind`
is `primary | outline | inverse | submit | text` — five *jobs*, not five styles, because a page
needs more than one button. `Testimonial.mode` is `single | grid`, and the component gained an
explicit `reviews` array so a page can place the remainder of its rows rather than silently
dropping them; the placement rule is prose in `rules/copy.md`. Every other `variant` prop is
gone, and `tests/py/test_design_picks.py::test_after_prune_no_variant_prop_remains` fails if one
comes back.

**Kit conventions.** Ten of them, written into the header of `src/components/kit/_registry.ts`
after the Task 5 quality review and binding on Tasks 6–15: no second `<main>`; focus rings read
`var(--kit-ring)` rather than a fixed focus token, because `--color-focus` is the same steel as
the inverse surface and a fixed ring vanishes on dark bands; colour from `currentColor` or a
context variable with a default; `Props extends HTMLAttributes<'tag'>` with `...rest` spread and
`class:list`; content through named slots, size/mode/data through props; overridable rules inside
`@layer components`; registration with demo fixtures; a dist assertion in
`test_design_components.py`; a primitive needed by a second component moves to
`src/styles/kit.css` (`.kit-card`, `.kit-card--lift`, `.kit-chip`); and convention 10 — a
*positional* check is inert on a preview page, because every demo is the first child of its own
section, so those checks are covered by fixture pairs under `tests/render/fixtures/` instead.

**`/kit-preview/`** replaces the deleted `/design-canvas/` route (amendment 4a). It is
`noindex`, renders one section per component from `_registry.ts` with no per-component branch,
and is the source the artboard builder cuts from and the only place the per-component dist
assertions can point at until project 4 mounts the kit on real pages.
`tests/py/test_design_components.py::test_no_canvas_route_after_prune` keeps the old route
deleted, and `form_contract_audit.py`'s `NON_CONTENT_ROUTES` names `kit-preview` with a
self-expiry test that requires the directory to exist.

## Second-run confirmation

§9.1–9.3: every check runs twice; both runs must be clean.

The full pipeline — `build` → `check:all` → `test:py` → `test:render:meta` →
`test:render:pages` → `build_scorecard.mjs --run first` → `baseline` — ran twice back to back
into `docs/reports/design-system-run.log`. The two halves are **identical after normalising
times**, verified programmatically rather than by eye.

**The method, stated so it can be repeated.** The log is split on `=== RUN 2 ===`. Each half is
reduced to a list of lines with: ANSI colour escapes stripped; `[WebServer]` request-log lines
dropped (one line per HTTP request from the Playwright fixture server, whose interleaving across
workers is nondeterministic by construction); leading `HH:MM:SS` clock stamps removed; every
elapsed-time form (`1.6m`, `91.16s`, `(+3ms)`, `(0:01:31)`) replaced by `T`; Astro's asset
ordinals `(8/46)` replaced by `(N/N)`; and Playwright's per-test ordinal (`✓ 104 [vp768] › …`)
replaced by `N`, because Playwright numbers tests in completion order across parallel workers.
The two normalised lists are then compared as **multisets**, so that a line appearing in a
different position but the same number of times counts as identical:

```
run1 normalised lines: 1673
run2 normalised lines: 1673
multiset differences : 0
```

Zero differences. Every summary line is therefore the same on both runs: build `51 page(s)
built`; parity `40 pages, 0 failing`; redirects `2186 internal refs; 0 problems`; schema
`51 pages; 0 blocking, 0 advisory`; sitemaps `51 built pages, 5 shards, 35 sitemap urls; 0
problems`; placeholders `1605`; marker `240 files; 0 problems`; agents `36 agents; 0 problems`;
pytest `1353 passed, 7 skipped, 1 xfailed`; meta `324 passed, 36 skipped`; pages `8 passed, 46
failed`; scorecard `261 defect ROWS across 18 pages`; baseline `0 problems`.

Before the normalisation was applied the raw diff showed 350 differing lines and, after dropping
the request log, 18 — nine tests whose Playwright ordinal differed by one between runs. Both
classes are ordering, not outcome; the multiset comparison is what proves that.
